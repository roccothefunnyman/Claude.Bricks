What is Claude.Bricks?

Claude.Bricks is a hands-on Azure ML project that trains machine learning models to assist in designing modular LEGO buildings from natural language descriptions. The pipeline runs from data ingestion through model deployment, orchestrated by Claude Code AI agents that coordinate every stage: uploading training data to Blob Storage, extracting features from LDraw files and rendered images, submitting Azure ML training jobs, and deploying models to managed online endpoints that the agents themselves call via HTTP.

Claude.Bricks also serves as a practical study project for the Microsoft DP-100 (Designing and Implementing a Data Science Solution on Azure) certification exam. Every exam domain is covered through a single, cohesive project with a real use case (making LEGO buildings from words) so the concepts stick better than isolated toy examples.

12. How the Models Work Together

This section covers how the four deployed ML models integrate back into the LEGO design workflow, how Claude Code is configured to call them, and what works today vs. what's still planned.

The Goal

You describe a building in plain English, and the system produces a valid LDraw (.ldr) file you can open in BrickLink Studio. Getting there requires four trained models working in sequence, with Claude Code acting as the orchestrator that ties them together.

Today, Claude Code already generates LEGO buildings from natural language by writing PowerShell scripts that output .ldr files. That works, but the design decisions are all based on Claude's general knowledge and whatever reference files you feed it. The deployed models will add domain-specific intelligence at each step: generating structured specs from prompts, classifying architectural styles, validating structural integrity, and pulling proven construction patterns from the training data.

The Integration Flow

When all four scenarios are deployed, a design session works like this:

  1. Spec generation (Scenario 4): You give Claude Code a natural language prompt. Claude calls the Spec Generator endpoint, which uses RAG (AI Search over the training data plus Azure OpenAI) to produce a structured building specification: dimensions, floor count, style classification, color assignments, window/door positions, and architectural features.
  2. Style validation (Scenario 1): If the spec references a known architectural style, Claude can optionally call the Facade Classifier endpoint to check whether the proposed design elements are consistent with that style. This is a sanity check, not a gate.
  3. Script generation: Claude writes a PowerShell script based on the spec, runs it, and produces the .ldr file. This step is the same as today, but informed by model output rather than general knowledge alone.
  4. Structural validation (Scenario 2): Claude sends the generated .ldr file's features to the Structural Validator endpoint. The Isolation Forest model flags anomalies (parts floating in space, walls with no foundation, collision-prone placements). If issues come back, Claude fixes the script and regenerates.
  5. Pattern lookup (Scenario 3): For specific construction challenges (cornices, roof lines, window arrangements), Claude can query the Pattern Extraction endpoint to retrieve proven patterns from the training data clusters. This helps when the design calls for something Claude hasn't seen in its reference files.

Configuring Claude Code to Call the Endpoints

There are two practical approaches. Both work, and they can coexist. Start with Option A because it takes five minutes. Move to Option B if the curl approach feels clunky after real use.

Option A: CLAUDE.md Instructions + .env File

The simplest approach. Store endpoint URIs and keys in a .env file (gitignored, never committed), and add usage instructions to CLAUDE.md. Claude Code reads CLAUDE.md at the start of every session, so it knows the endpoints exist and how to call them.

.env (gitignored)

# Azure ML Endpoint Configuration
AZURE_ML_SPEC_ENDPOINT=https://spec-generator.eastus.inference.ml.azure.com/score
AZURE_ML_SPEC_KEY=abc123...
AZURE_ML_VALIDATOR_ENDPOINT=https://structural-validator.eastus.inference.ml.azure.com/score
AZURE_ML_VALIDATOR_KEY=def456...
AZURE_ML_CLASSIFIER_ENDPOINT=https://facade-classifier.eastus.inference.ml.azure.com/score
AZURE_ML_CLASSIFIER_KEY=ghi789...
AZURE_ML_PATTERNS_ENDPOINT=https://pattern-library.eastus.inference.ml.azure.com/score
AZURE_ML_PATTERNS_KEY=jkl012...

Claude Code constructs curl commands during design sessions based on these instructions. It already knows how to run bash commands, so no new tooling is required.

Option B: MCP Server (Native Tool Integration)

A more polished approach. Build a small MCP (Model Context Protocol) server that wraps the Azure ML endpoints as Claude Code tools. Instead of constructing curl commands, Claude gets native tools like generate_spec, validate_structure, and get_patterns that it can call directly.

.claude/settings.json

{
  "mcpServers": {
    "claude-bricks-ml": {
      "command": "node",
      "args": ["mcp-server/index.js"],
      "env": {
        "AZURE_ML_SPEC_ENDPOINT": "https://...",
        "AZURE_ML_SPEC_KEY": "..."
      }
    }
  }
}

What Claude Code sees

Available tools from claude-bricks-ml:

generate_spec(prompt, dimensions)
  // Calls Scenario 4 endpoint
  // Returns structured building spec

validate_structure(ldr_features)
  // Calls Scenario 2 endpoint
  // Returns anomaly scores

classify_facade(image_path)
  // Calls Scenario 1 endpoint

get_patterns(feature_type)
  // Calls Scenario 3 endpoint

The MCP server itself is roughly 100-150 lines of Node.js. It's a thin wrapper that receives tool calls from Claude Code and forwards them as HTTP POST requests to the Azure ML endpoints. The advantage is cleaner integration: Claude Code treats the models as first-class tools rather than bash commands, and the server handles authentication, error formatting, and response parsing in one place.

Why No Frontend?

Claude Code already provides the user interface: you type what you want, Claude builds it. Adding a web frontend would be a separate project with its own deployment and maintenance costs, and it wouldn't add much for this use case. The models are deployed as REST endpoints, so Claude Code calls them the same way it would call any API. If a frontend becomes useful later (for demo purposes, or to let non-technical users try it), the endpoints are already there to support it.
