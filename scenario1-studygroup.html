Discuss: Blue/Green Canary Rollout

Step 8 from the full walkthrough, adapted for discussion

When you retrain and register a new model version, deploy it as a canary alongside the existing blue deployment. Traffic shifting is a metadata operation on the endpoint. It takes effect in seconds and can be reverted instantly.

The Rollout Pattern

Green 0%

The Commands

Terminal
# Deploy new version as "green" with 0% traffic python deploy_canary.py \ --model-name facade-classifier \ --model-version 2 \ --endpoint-name facade-classifier-endpoint \ --deployment-name green # Smoke test only the green deployment before shifting any traffic python smoke_test.py \ --endpoint-name facade-classifier-endpoint \ --deployment-name green \ --num-requests 5 # Shift 10% to green, observe, then 50%, then 100% python promote_deployment.py --endpoint-name facade-classifier-endpoint --deployment-name green --traffic 10 python promote_deployment.py --endpoint-name facade-classifier-endpoint --deployment-name green --traffic 50 python promote_deployment.py --endpoint-name facade-classifier-endpoint --deployment-name green --traffic 100 # If green shows problems at any point, rollback instantly python rollback_deployment.py \ --endpoint-name facade-classifier-endpoint \ --target-deployment blue \ --delete-failed
Rollback is a metadata operation
Traffic shifting does not provision or destroy any infrastructure. The deployment stays running at whatever traffic weight you assign. Rollback takes effect in seconds.

Discuss: Drift Monitoring Concepts

Step 9 from the full walkthrough, adapted for discussion

After a model is in production, the distribution of incoming requests may drift from the distribution of the training data. The monitoring/drift/ scripts establish a statistical baseline and compare future inference data against it on a weekly schedule.

How It Works

Terminal
# Step 1: Create a baseline profile from training data python create_baseline.py \ --training-data ../../deploymentcode/data/scenario1/features.csv \ --output baseline_profile.json # Outputs per-feature statistics: mean, std, percentiles, histograms # Step 2: Compare future inference data against the baseline python detect_drift.py \ --baseline baseline_profile.json \ --inference-data recent_inference_data.csv \ --psi-warning 0.2 \ --psi-critical 0.4 # Exit code: 0=none, 1=warning, 2=critical

Lessons Learned During Setup

These are the issues that came up when running the pipeline end-to-end for the first time. Each one is a realistic problem you will encounter in practice, and several map directly to AI-300 exam topics.

1

Custom Conda Environment Broke the AML Executor Silently

Environment base image compatibility with Azure ML job runtime
The Problem

The custom claudebricks-sklearn environment uses openmpi4.1.0-ubuntu22.04 as its base image. Jobs submitted with this environment would appear to start, then fail at the executor initialization stage without a clear error message in the job logs. The failure was silent: the job status moved to Failed but the log output gave no Python traceback, just a generic executor startup error.

Fix: Switch to the Azure ML curated environment sklearn-1.5 for this training run. Curated environments are pre-validated against AML infrastructure and have no base image compatibility issues.

What this means for the exam

AML curated environments (prefixed AzureML- or available by short name like sklearn-1.5) are maintained by Microsoft and tested against the AML execution infrastructure. Custom environments built from community base images can have incompatibilities that only surface at runtime. When a job fails at executor startup with no Python-level traceback, the environment is the first thing to check.

Environment TypeBuild TimeCompatibility RiskWhen to Use
Curated (sklearn-1.5)Zero (pre-built)NoneStandard workloads matching a curated offering
Custom (conda spec)5-15 min first runPossible base image issuesWhen you need packages not in any curated environment
2

MLflow 3.x Broke AML Experiment Tracking

API version mismatch between the MLflow client and the AML tracking server
The Problem

MLflow 3.10.1 added a new internal API call to /api/2.0/mlflow/logged-models when mlflow.log_model() is called. The AML tracking server (which hosts the MLflow-compatible API) does not implement this endpoint yet. The call returned 404, which caused the training script to fail during model logging even though the training itself had completed successfully.

Fix: Pin mlflow>=2.10.0,<=2.16.2 in the environment or requirements. The 2.x series uses only API endpoints that the AML tracking server supports.

What this means for the exam

AML's MLflow-compatible tracking server is compatible but not identical to a standalone MLflow tracking server. The AML server supports the core experiment, run, metric, parameter, and artifact APIs. Newer MLflow client versions may call additional endpoints that the AML server has not implemented. Pin your MLflow version in all AML job environments.

3

vCPU Quota Was Fully Consumed by the Compute Cluster

VM family quotas are shared across all AML compute in a region
The Problem

The DSv2 VM family quota in East US 2 was 6 cores. The training compute cluster (cpu-cluster, Standard_DS3_v2, max 2 nodes) already occupied all 6 cores at maximum scale. When the endpoint deployment tried to create a managed online endpoint instance using Standard_DS3_v2, it failed with a quota exceeded error.

Fix: Deploy the endpoint using Standard_F2s_v2 (Fsv2 family), which has a separate quota pool. The endpoint uses 2 vCPUs from the Fsv2 quota and does not conflict with the DSv2 training cluster.

What this means for the exam

Azure vCPU quotas are per VM family, per region, per subscription. A single quota limit can block multiple different resource types (compute clusters, managed endpoints, AKS nodes) that all use the same VM family. Choosing different VM families for training and inference workloads avoids this conflict. Quota increases can be requested in the Azure portal under Subscriptions → Usage + quotas.

ResourceVM SizeVM FamilyvCPUs Used
cpu-cluster (max scale)Standard_DS3_v2DSv28 (4 per node x 2 nodes)
facade-classifier-endpointStandard_F2s_v2Fsv22
Quotas are checked at deployment time
Azure does not pre-reserve quota when you define a compute cluster or endpoint. The quota check happens when nodes are actually provisioned. A cluster with max_nodes=2 only consumes quota when jobs are actively running and nodes have scaled up.
4

Relative Path in prepare_data.py Broke When Run from Different Directories

Python scripts in AML jobs run from a different working directory than expected
The Problem

The prepare_data.py script used a relative path like ../data/facade-images to locate the source images. When called from a different directory than expected, Python resolved the relative path against the current working directory (which was different), and the script failed with a FileNotFoundError.

Fix: Use Path(__file__).parent to build paths relative to the script file's location, not the calling directory. This works regardless of where the script is invoked from.
Python
# Fragile: depends on where you run the script from data_dir = "../data/facade-images" # Robust: always relative to this script's location from pathlib import Path data_dir = Path(__file__).parent / "../data/facade-images"
5

smoke_test.py Had Two Bugs: Missing Request File and Double-Serialized JSON

SDK invocation API details and endpoint response format
Bug 1: request_file=None

The AML SDK's online_endpoints.invoke() method requires a request_file parameter pointing to a file on disk. Passing request_file=None caused an SDK-level error before the request was even sent.

Fix: Write the request payload to a temp file and pass that file's path to invoke().
Bug 2: Double-Serialized JSON Response

The scoring script returned a JSON string. The SDK wrapped that in another JSON string during transport. The smoke test tried to parse the outer string as JSON and got a prediction of "{\"prediction\": \"historic\"}" instead of {"prediction": "historic"}. The raw result was a string containing a JSON-encoded string, not a dict.

Fix: Call json.loads() twice when the result is a string, or handle both cases: if the result is already a dict, use it directly; if it is a string, parse it.
Python
# Double-parse the response to handle double-serialized JSON raw = ml_client.online_endpoints.invoke( endpoint_name=endpoint_name, request_file=tmp_path ) result = json.loads(raw) if isinstance(result, str): result = json.loads(result) prediction = result["prediction"]
