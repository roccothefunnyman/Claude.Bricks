5. Scenario 1: Facade Style Classification

1

Image Classification Pipeline

Train a Random Forest classifier on facade images to categorize architectural styles (historic, modern, industrial, commercial, residential).

Scenario 1: End-to-End ML Pipeline
Images flow from Blob Storage through a data asset to the training cluster. The trained model is registered in MLflow, then deployed to a managed online endpoint for real-time inference.

6. Scenario 2: Structural Validation (Anomaly Detection)

2

Anomaly Detection on LDraw Files

Parse .ldr files into numeric features, then use Isolation Forest or Random Forest to flag structurally unsafe LEGO builds.

Scenario 2: Feature Engineering + Anomaly Detection Pipeline
Raw .ldr files are parsed into 4 numeric features. An anomaly detection model (Isolation Forest or Random Forest) classifies structures as pass/fail. Deployed as a managed endpoint consumed by the Claude.Bricks validator agent.

7. Scenario 3: Pattern Extraction (Clustering)

3

Multi-Step Pipeline: Extract → Cluster

Discover common building patterns across reference .ldr models using part-usage statistics and clustering (KMeans/HDBSCAN). This is a batch/offline analysis -- no real-time endpoint required.

Scenario 3: Azure ML Pipeline (2-Step)
A two-step Azure ML Pipeline: Step 1 extracts part-usage features from .ldr files, Step 2 runs clustering. The @dsl.pipeline decorator chains steps, passing the features output from Step 1 into Step 2.

8. Scenario 4: Fine-Tuned LLM Spec Generator

4

RAG + Fine-Tuning with Azure OpenAI

Generate detailed LEGO building specs from natural language prompts. Uses Retrieval-Augmented Generation (AI Search) and optionally fine-tunes gpt-4o-mini on domain-specific spec examples.

Scenario 4: RAG + Fine-Tuning Architecture
The RAG pipeline uses Prompt Flow to chain retrieval (AI Search vector query) with generation (Azure OpenAI). Fine-tuning is optional and replaces the base gpt-4o-mini deployment with a domain-specialized model.

9. Data Flow Overview

How Data Flows Across All Scenarios
Data flows left-to-right: Blob Storage → Datastores → Compute clusters → Model Registry → Online Endpoints → Clients. MLflow tracks all experiments. Each scenario uses its own blob container and produces its own registered model.

11. Teardown Procedure

Tear down in order of cost priority: endpoints first, then compute, then full destroy.

Step 1
Delete Online Endpoints
az ml online-endpoint delete
→
Step 2
Delete FT Deployment
az cognitiveservices ... delete
→
Step 3
Stop Compute Instance
az ml compute stop
→
Step 4
Terraform Destroy
terraform destroy
# 1. Delete endpoints (highest hourly cost)
az ml online-endpoint delete --name facade-classifier-endpoint --yes
az ml online-endpoint delete --name ldr-validator-endpoint --yes

# 2. Delete fine-tuned model deployment (~$1.70/hr)
az cognitiveservices account deployment delete \
  --name <openai-resource> --resource-group $RESOURCE_GROUP \
  --deployment-name ft-spec-generator

# 3. Stop compute instance
az ml compute stop --name ci-dev-dev \
  --resource-group $RESOURCE_GROUP --workspace-name $ML_WORKSPACE

# 4. Full destroy (deletes ALL resources including RG)
cd deploymentcode/terraform
terraform destroy
